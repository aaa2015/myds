# 视觉（图片输入）—— DeepSeek-V4.1-Flash-Vision

状态：**已交付并在生产运行**（2026-10-01）。本文是使用与维护入口。

---

## 怎么用

启动时给一个编码器路径即可（其余全自动）：

```
myds -m <主模型.gguf> --vision <视觉编码器.gguf> --port <端口> ...
```

- **不给 `--vision`** ⇒ 纯文本模式，行为与以前完全一致。
- **给了但加载失败** ⇒ 服务照常启动，**降级为纯文本**，原因写在日志里。
  （理由：配置里写错一个路径不该把整个服务拖down。）
- 舰队部署：`fleet.conf` 的第 18 列 `MULTIMODAL=1` 会自动带上 `--vision`；
  **声明为 1 但目录里找不到 `*Vision*.gguf` ⇒ 拒绝启动**（见下「能力声明必须同源」）。

### 请求格式

Responses API 与 Chat Completions 都接受，`image_url` 可以是字符串或 `{"url": ...}` 对象：

```jsonc
{"input":[{"role":"user","content":[
    {"type":"input_image","image_url":"data:image/jpeg;base64,/9j/4AAQ..."},
    {"type":"input_text","text":"这张图里有什么？"}]}]}
```

- **只接受内联 `data:` base64 URL**，不接受远程 `http(s)`（不替调用方取远程资源）。
- **一条请求里可以出现多个图片块**（客户端重发历史所致），每个块独立注入。

## 原理

### 图片块是一段「同一 id、不同向量」的位置

V4.1 的图片块在序列里**所有位置共用同一个 token id**（`129264` = `<｜deepseek_image｜>`），
真正的区分在**逐位置的向量**上：

```
[START] + 每行( width 个 IMAGE + 1 个 NEWLINE ) + [END]
  START  → image_start   哨兵向量（编码器 GGUF 里学出来的张量）
  IMAGE  → 编码器对该格输出
  NEWLINE→ image_newline 哨兵
  END    → image_end     哨兵

token 数 = h*(w+1) + 2        网格用【下采样后】的 llm 网格 = ceil(patch_grid/3)
```

词表查表做不到「同一个 id 出多个向量」⇒ 引擎单独提供了一段 **按位置注入向量** 的接口：

```
myds_context_set_image_embeddings(ctx, start_pos, count, data, dim);
```

两条 V4.1 路径（批量 prefill、单 token）都会先查这个区间，命中就用注入向量，
否则照常查表。注入是**拷贝**，调用方不必管生命周期；下一次生成前会被覆盖/清除。

### 占位符的取值与校验

占位符文本（`<｜deepseek_image｜>`）**不是写死的常量**，而是：从视觉文件的元数据取
`image.token_id` → 到**主模型词表**里查它的文本 → **验证往返**（该文本编码回来必须
恰好是 1 个 token）。不满足就**拒绝启用视觉**。

理由：占位符若要占 N 个位置，tokenizer 就必须把它编成 **恰好 1 个** token；
只要它编成 0 个或 2 个，图片块占的位置数就与向量数不符 —— 向量会贴到错的 token 上，
**而且不报错**。

### 偏移量的算法

图片块的起始 token 下标 = **把「占位块之前的文本」编码一次**得到的 token 数。
`add_bos` 必须与引擎内部分词一致（差 1 就整体错位）。

## 验证（可复跑）

| 项目 | 命令 / 方法 | 结果 |
|---|---|---|
| 解码/预处理/布局 与 ds4 逐字节对拍 | `make vis-crosscheck` | **13/13** |
| 9 个视觉内核独立探针 | `tools/vis_kprobe.c` | **5/5 全过** |
| 权重加载无损 | 全量 F32 vs BF16→F16 | F32 全精确；F16 有 3M 个值错、最大差 3.02 |
| 与 ds4 参照**逐阶段**对拍 | `tools/vis_ref_ds4.sh` | early 3.6e-5 → aligned 2.9e-2，**平滑无跳变** |
| F64 真值复核 | 用文件原始权重重算 patch_embed | **12/12 两侧相同**，差 ≤1 个 BF16 ULP |
| 端到端 | 三组对照（图一/图二/无图） | 答案随图不同、读**出图内实际文字** |
| 跨机真服务 | 开发机 → 部署机（HTTP 调用） | 正常 |

**关于与 ds4 的 2.9e-2 差异（已知并已定性）**：两侧都用 F32 累加，但分块/归约次序不同
（本仓 `simdgroup_float8x8` vs ds4 的 `glm53_mul_mm_bf16_t`），每层末尾又都舍到 BF16，
于是边界附近的值会翻 1 个 ULP；32 层累积到 ~3%。**不是实现错误，是 BF16 量化的固有敏感性**
（F64 真值复核已排除「哪一侧更准」的问题）。

## 范围：明确**不做**的（2026-10-01 决定）

| 不做 | 理由 |
|---|---|
| **「多图」当特性来做**（多图对比/多图推理） | 不需要。用户一次只发一张图 |
| **远程 URL 取图**（`http(s)://`） | 不需要；且「服务端替调用方取远程资源」是策略决定，不默认打开 |
| **图片块进前缀缓存** | 不需要。图片块目前每次重算，代价见下 |

> ⚠️ **但服务端【必须】容得下一条请求里出现多个图片块** —— 这不是特性，是**客户端行为决定的**：
> 常见客户端会**保留最近若干回合的图片并随每轮请求重发**（更早的才被替换成
> `[image data removed - already processed by model]`）。
> `[image data removed - already processed by model]`）。
> 于是「发过图 → 追问 → 再发图」几轮之后，一条请求里天然会攒到 2~3 个图片块。
>
> **2026-10-01 曾因此线上报错**：服务端对「一次一张」的人造上限直接整单拒绝，
> 而报错文案只说 `unsupported content block`，看不出是数量限制。
> 现已改为**遍历所有图片块**，并按内容哈希缓存重发的图
> （实测第 6 轮：3 个区间、全部命中缓存、prefill 只跑 12 tok、0.58s 完成）。

## 其他已知边界

- 图片块**每次请求全量 prefill**（不进 prefix cache）。实测 ~500 占位 token 的图
  prefill 在 2.1s 量级（241 t/s）。
- 编码器权重按 **F32** 上传（1.81 GiB）。**不要**改成 F16：实测 294 万个值有 3M 个不符、
  最大差 3.02（相对 118 倍），会让数值整体走样。
- 图片编码本身约 **6s/图**（jpg 解码 + 预处理 + 32 层编码），与 prefill 分开计时。

## 排障

**「发图之后再正常对话就 400」** —— 先看服务端日志里那句 `input_image 被拒: …`。
若写着「一次请求只支持一张图」，那是旧版本的人造上限（客户端会保留最近 3 个回合的图片并重发）。
新版本不设上限，并对重发的图按内容哈希缓存。

**日志里看到 `input_image 被拒: ...`** —— 每条拒绝都会写出**具体原因**（字段缺失 / 不是
data URL / base64 解码失败 / 服务端未启用视觉 / 一次只支持一张图）。照着那一句查。

**提示词里系统提示词出现两遍 / `prompt_chars` 翻倍** —— 客户端可能【同时】发
`instructions` 字段、又在历史里带一条 system 消息。
服务端规则：**历史里有 system 消息 ⇒ 以历史为准，跳过 `instructions`**（并保持渲染稳定）。
两边文本不同时会记一条 WARN —— 那是唯一会丢内容的路径，不静默做。
判定用探针量：`tools/vis_dup_probe.c`（数渲染结果里出现的次数，不看代码）。

**服务启动后日志说「多模态已启用」但收到图就 400** —— 检查启动命令行里**有没有 `--vision`**。
`MULTIMODAL=1` 是**给网关的能力声明**，`--vision` 才是**真实能力**；两者必须同源。
（曾经不同源：声明=1 而无 `--vision`，服务照常启动、日志还打「已启用」，
网关把图片路由过来才 400。现已改为「声明=1 就传 `--vision`；找不到编码器就拒绝启动」。）

**怎么确认视觉真的在跑**（不要只看配置）：

```sh
ps -o command= -p <pid> | tr ' ' '\n' | grep -A1 -- --vision   # 实参
grep -E "视觉编码器已就绪|视觉占位符" <日志>                    # 运行时真状态
```
