本文档记录从 **Project Maya (`mw00/project-maya`)** 调研、**验收**并（部分）落地至 **myds** 推理引擎的架构与设计优化。

> **当前状态（2026-11-01）**：三项中只有 LoopGuard 的**检测器本身**被保留，
> 但默认关闭（假阳性未测）。优化 1 的前提被实测证伪，代码保留为 opt-in 测量工具。
> 优化 3 是模型侧建议，数字已重算，尚未上线验证。逐项裁定见 §4。

## 一、 优化 1：基于物理代价模型的自适应投机解码控制器

### 1.1 问题背景与痛点
在 `myds` 的前期实验（账本 §100/§101）中：
* **PLD（Prompt Lookup Decoding）投机实测 −6.6%（倒亏）**；
* **DSpark 投机实测：最高 11.1% 接受率 × 3.04× 验证成本 ⇒ 净慢**。

**瓶颈根因**：
在 MoE 架构中，验证多 Token 时，各 Token 路由到的专家是**并集关系**，独立专家数 $U(k)$ 会随推测步长 $k$ 迅速膨胀。加之快照状态暂存与回滚的固定开销，推测验证步的相对耗时约为单步解码的 $1.25\sim1.35$ 倍。若草稿接受率 $q$ 较低（如 $q < 0.35$），单步期望产出无法抵消额外开销，投机必定导致端到端吞吐下降。

### 1.2 Maya 的解法与落地实现

> ⚠️ **2026-11-01 验收改判：本项不采纳为默认路径，代码保留为 opt-in 测量工具。**
>
> 验收查出三个问题，见 §4.1。结论先说：
> 1. **该控制器在生产路径上不执行。** native V4.1 + batch2-spec=0 + DSPARK=0 时
>    `pld_enabled = use_spec && ...` 为 false（`myds_engine.c`），PLD 循环根本不进入。
>    账本 §77.x 已写明「保留 `MYDS_PLD=1` 不等于本轮实际运行 PLD」，每 sample 的
>    PLD queries/cycles/accepted 实测全为 0。**因此「消除 −6.6% 倒亏」从未在任何
>    生产配置上被测量过。**
> 2. **代价模型与仓库自己的实测矛盾。** 本节假设验证开销 1.25–1.35×，据此推出
>    收支平衡点 q ≈ 0.28（代码取 0.38）。但账本 §100.3 记的是 PLD 验证
>    **49.18 ms/call**，§4.16 同口径单步 **23.55 ms/token** ⇒ **2.09×**。
>    本次在生产进程上实测到 **2.04×**（48.5 ms/call 对 23.81 ms/token），
>    与账本一致。**即使接受率 100%，一次验证也只能做到 48.5/2 = 24.25 ms/token，
>    仍比单步 23.81 ms 慢 1.9%** ⇒ 这条路径在结构上不可能有正收益。
>    门禁的价值不是「变正」，是**止损到零**（实测见 §4.7）。
> 3. **门禁在默认配置下会永久关死 37% 的草稿。** 默认 `min_ngram=2 / max_ngram=4`，
>    可达桶只有 0/1/2（桶 3 的 ng≥5 不可达）。桶 0 先验 0.35 < 阈值 0.38 ⇒
>    `decode_pld_propose` 每次都提前返回 0 ⇒ 该桶的 EMA 更新代码永远执行不到。
>    真实文本实测（60k token）：proposals 43133，其中 **ng2 占 36.8%**，被一刀切死
>    且永远不会被重新评估。
>
> 现实现：`spec_adaptive` 由 `MYDS_SPEC_ADAPTIVE=1` 显式开启，默认 **0**，
> 默认行为与改动前完全一致；开启后仍有 `SPEC_ADAPTIVE_MIN_SAMPLES=3` 的强制试探，
> 让桶 0 有机会被观测。`pld_queries` 也已改为只统计真正送进验证的草稿，
> 否则与账本 37.3% 的历史读数不可比。

参考 Maya 的 `src/spec/controller.cpp`，我们在 `include/myds_pld.h` 与 `src/myds_engine.c` 中加入了基于匹配长度的先验与 EMA（默认关闭，见上）：

1. **扩展 PLD 草稿提取**：
   * 增加 `myds_pld_propose_ex`，在检索匹配的同时输出实际命中的 N-gram 长度 `matched_ng`。
2. **N-gram 长度分桶与先验**：
   * 桶 0（$N=2$）：先验接受率 $0.35$
   * 桶 1（$N=3$）：先验接受率 $0.60$
   * 桶 2（$N=4$）：先验接受率 $0.80$
   * 桶 3（$N \ge 5$）：先验接受率 $0.92$
3. **收支平衡门禁（Breakeven Safeguard，`MYDS_SPEC_ADAPTIVE=1` 才生效）**：
   $$\text{Expected Tokens} = 1.0 + q$$
   实现里用的阈值是 $q \ge 0.38$（按 1.28× 成本推出 0.28 后再留余量）。
   这个阈值在 2.04× 的真实成本下**推不出正收益**（需要 $q \ge 1.04$），
   但它能**砍掉低接受率桶，把损失压回零**：生产实测 −7.1% → 0.0%（§4.7）。
   所以它的定位是止损阀，不是加速器。
4. **在线自适应学习**：
   每次验证完成后以 $\alpha = 0.15$ 做 EMA 平滑更新：
   $$q_{\text{new}} = (1 - \alpha) \cdot q_{\text{old}} + \alpha \cdot \text{hit}$$
   同时累计每桶样本数；关禁开启时，样本不足 3 次先强制试探，否则先验 0.35 < 0.38
   会让桶 0 一张草稿都发不出去，EMA 永远停在初值上。
   ~~在代码、结构化文本等高频模式下自动加速……彻底消除负收益。~~
   **该句已撤回：没有任何生产配置下的测量支持它。**

## 二、 优化 2：LoopGuard 服务端周期性死循环检测与自愈

### 2.1 问题背景与痛点
在超低比特量化（Q2_K / IQ2）以及长思维链（`<think>`）生成过程中，大模型在贪婪采样（`temperature=0`）或特定提示词下存在退化为**无限周期死循环**的物理风险（如连续循环输出某一段 4~64 token 的代码、模板或字符），直到打满 `max_new_tokens`，严重浪费 GPU 显存带宽与算力。

### 2.2 Maya 的解法与落地实现
参考 Maya 的 `serve/loop_guard.py`，实现了轻量级环形历史检测器 `include/myds_loop_guard.h` 并接入生成流：

1. **滑动窗口周期检测**：
   * 维护容量 1024 的 Token 历史环形缓冲；
   * 针对周期 $P \in [4, 256]$：
     * 短周期（$P < 16$）：检测到连续重复 4 次即判定死循环；
     * 长周期（$P \ge 16$）：检测到连续重复 3 次即判定死循环；
2. **停止语义与上报**（2026-11-01 修正）：
   * 命中后输出警告日志，停止原因置为**独立的 `MYDS_STOP_LOOP_GUARD`**，
     不再冒充 `MYDS_STOP_EOS`——冒充 EOS 会让半截回答看起来像正常收尾；
   * 服务端把这个原因映射为 `finish_reason: "length"`：输出确实被截断了，
     客户端必须能分辨。映射成 `"stop"` 是原实现的缺陷。
3. **环境开关（默认关闭）与真机假阳性实测**：
   * 通过 `MYDS_LOOP_GUARD=1` 显式开启；默认 **关闭**。
   * **在 macstudio 上用真实模型输出实测**（`DeepSeek-V4.1-Flash-1017-Q2`，
     `temperature=0`，真实 GGUF tokenizer 分词，检测器与原实现逐字一致）：

     | 任务 | tokens | 触发 |
     |---|---:|---:|
     | markdown 表格（5 种排序算法） | 321 | 0 |
     | 10×10 乘法表代码 | 60 | 0 |
     | 西湖历史（中文散文） | 187 | 0 |
     | B-tree vs B+ tree（英文） | 311 | 0 |
     | REST 项目目录树 | 400 | 0 |
     | 2008–2020 中国 GDP 表 | 388 | 0 |
     | 二叉搜索树完整实现 | 2,291 | 0 |
     | 80 个 Linux 命令 | 2,499 | 0 |
     | transformer 注意力讲解 | 2,120 | 0 |
     | **合计（9 个正常任务）** | **8,577** | **0** |

   * **结论：正常任务上的假阳性为 0，检测器不会打断表格、框线或代码。**
     （下文记录了一次被撤回的相反读法：用粗粒度分词器在同一批源文件上得到的
     「表格行会触发」是**分词器假象**，真实 BPE 下同一批文本零触发。）
   * **阳性对照有效**：明确要求重复的任务会被正确拦下 ——
     把 `ERROR: connection timed out after 30s` 重复 30 遍 ⇒ 第 119 token 触发
     （period=10, reps=4）；重复输出同一段错误处理代码 20 遍 ⇒ 第 125 token 触发
     （period=21, reps=3）。检测能力确认真实存在。
   * **仍然默认关闭的真实理由**：它分不清「模型失控的循环」和「用户要求的重复」。
     后者的合法场景（生成日志模板、批量样板代码、压力测试数据）会被直接截断。
     这个缺陷在真机上一测即现，和上面 0 假阳性是同一批实验的两面。
4. **开销实测**（可忽略）：随机流 0.20 µs/token；极端周期流 0.26–0.58 µs/token，
   相对单步解码 ~23.5 ms 完全可忽略。检测器本身不是问题，假阳性才是。
5. **单测已纳入 `make test`**：`tests/test_loop_guard.c` 原提交没进 Makefile，
   等于零回归保护；现已作为 `TEST_LOOP_GUARD` 注册。

## 三、 优化 3：MoE 专家非对称量化方案（模型侧演进建议）

### 3.1 理论依据
参考 Maya 的 DeepSeek-V4.1 量化配方（`tools/ds4/recipe_maya_s_test.json`）：
* **Down 投影**（`ffn.down`）：维度从 $2048 \to 5120$，负责聚合各特征通道并重构 Residual 流，数值敏感度远高于 Gate/Up；
* **Gate & Up 投影**（`ffn.gate`, `ffn.up`）：仅负责升维与门控筛选，对低比特容忍度极高。

### 3.2 建议的非对称量化规格
* **MoE Gate / Up**：保持 `Q2_K`（或 `IQ2_XXS`）；
* **MoE Down**：提升至 **`Q3_K`**（或 `IQ3_S`）；
* **关键张量保留**：`hc_`、`norm`、`engram`、`attn_sinks` 维持 `Q8_0` 或 FP8。

### 3.3 M2 Ultra 192GB 显存预算评估（2026-11-01 重算）

> ⚠️ 原表按「单专家 down 10.5 MB → 14.5 MB、增量 4 MB、全量 61.4 GB」算，
> 但这两个数与 Q2_K / Q3_K 的位宽对不上。按 `src/myds_v41_moe.c` 实际形状
> （`dim==5120 && width==2304`）重算：

* 40 层 MoE 共有 $40 \times 384 = 15360$ 个专家；
* 单专家 `ffn.down` = $5120 \times 2304 = 11{,}796{,}480$ 参数
  ($= 11.25$ MiB 的 FP16 等价量)；
* 按真实位宽计：

  | 精度 | bits/weight | 单专家 down |
  |---|---:|---:|
  | Q2_K | 2.625 | **3.69 MiB** |
  | Q3_K | 3.4375 | **4.83 MiB** |

* 单专家增量 $\approx 1.14$ MiB，全量 $15360 \times 1.14\text{ MiB} \approx$ **17.5 GB**；
* 原文档的 10.5 / 14.5 MB 对应约 7.1 / 9.8 bits-per-weight，不是 Q2_K / Q3_K。
  **61.4 GB vs 17.5 GB 差约 3.5×**，会改变「要不要分层/只升热专家」的取舍。
* 结论方向（能否塞进 192GB）可能仍成立，但必须先按 17.5 GB 这个量级重做预算；
  上线前需要同类对照实测（同 seed、同 prompt、只换 down 的量化档）。

### 4.3 本次修掉的缺陷

1. **`ctx->pos` 未发布**（4 处）：投机路径因 LoopGuard 早退时没写 `ctx->pos`，
   而同分支其它出口全都写。后果是 pos 落后真实 KV 状态 1–2 token，
   下个请求少复用 ≤2 token。已按各分支的 `spec_pos/pld_pos + 1u|2u` 补齐。
2. **`pld_queries` 口径**：原本在门禁前自增，把被拒的查询也算进去，

3. **`spec_pld_q` 用浮点值当初始化标志**：改成 `spec_prior_ready` 布尔位。
4. **纯自回归路径没有任何 LoopGuard 检查点**（真机实测才暴露）：原补丁 12 个检查点

5. **`test_http_bytes.c` 补的 `myds_context_find_steer` stub**：这是真实既存链接错误

   修复正确，但原提交信息一字未提 —— 补记于此。

### 4.5 LoopGuard 引擎级验证（2026-11-01，macstudio 8187）

> §4.4 验的是**检测器**（喂 token 会触发）。这一节验的是**引擎接入**（触发之后真的断）。
> 两者必须分开记录 —— 把它们混为一谈正是下面这个 bug 能活下来的原因。

**第一次跑就是失败**：`MYDS_LOOP_GUARD=1` 下，一个"重复 30 遍"的请求
报警 **260 条**，而输出与关闭时**逐字节相同**（`sha=ad477381fc750ed7`，1139 字符 / 299 token）。
即：它一直在喊，什么都没做。

**根因**：原补丁的 12 个检查点全在**投机分支**里。生产 `MYDS_BATCH2_SPEC=0`
⇒ `use_spec=false` ⇒ 走的是**纯自回归路径**，那条路径上没有任何 `loop_detected` 判断。
单测直接喂检测器、从不经过消费它的那个循环，所以"单测通过"和"端到端生效"完全脱钩。

**修两处**：

1. 纯自回归路径补检查点（该路径 `ctx->pos` 恒等于已消费数，不需要 spec_pos 偏移）；
2. `ctx->loop_detected` 一旦置位就**停止再喂** —— 否则历史里仍留着重复序列，
   之后每个 token 都会再报一次。

**修复后复测**（同一进程、同一批 prompt，开关两态对比）：

| 检查项 | 关闭 | 开启 | 结论 |
|---|---|---|---|
| 6 个正常任务 | 见下表 | **sha256 完全相同** | 0 假阳性，行为零变化 |
| 重复 30 遍 | 1139 ch / 299 tok / `stop` | **152 ch / 40 tok / `length`** | 正确截断 |
| WARN 条数 | 0 | **1**（原为 260） | 日志风暴已消除 |
| 截断后多轮续问 | — | 正常回答 | `ctx->pos`/前缀缓存一致 |
| 8 条 cyber32 官方 prompt | — | 0 命中 | 官方负载上无假阳性 |

正常任务逐一对照（sha256 前 16 位，两态完全一致）：

| 任务 | chars | tok | finish | sha |
|---|---:|---:|---|---|
| markdown 表格 | 660 | 321 | stop | `80d6e1499d27cec8` |
| 乘法表代码 | 215 | 60 | stop | `b262ce5820a5415f` |
| 西湖历史 | 273 | 186 | stop | `d0b31692dd83f382` |
| B-tree 对比 | 1604 | 311 | stop | `30d35309c67fed96` |
| 目录树 | 1111 | 400 | length | `9dd82ee6818cbe89` |
| 二叉搜索树 | 7150 | 2291 | stop | `b3f689baf206bdb9` |

**截断位置逐 token 核对**：40 = 周期 10 × 重复 4 次，正好是设计阈值，
不多砍也不少砍。

**⇒ 裁定**：引擎接入现在**真的验证过了**。但配置仍恢复为默认关闭 ——
理由是 §2.2 那条：它分不清"失控循环"和"用户要求的重复"，
而后者在 agent 场景里是合法需求。是否常开由统帅决定，现在有了数据支撑这个决定。

### 4.6 测量约束（为什么必须走生产 A/B）

macmini 上**没有 V4.1 主模型**（全盘 `find *.gguf -size +2G` 为空），
所以这项收益在本机根本无法测量。macstudio 上也不能另起实例：
生产进程 RSS 已 149.6 GiB / 整机 192 GB，第二个全量实例会撞内存墙
（`start_fleet.sh` 自己会拦，见 `s_host_memo_c3db60c9ea734f19a3fd` 记的 panic 前科）。

**唯一可行的口径**：在生产进程上串行受控 A/B —— 改配置、重启、测量、复原。
已于 2026-11-01 获授权执行，结果见 §4.7。

⚠️ 注意这里的口径陷阱：`MYDS_PLD=1`（生产 conf 里一直有的那个开关）
**并不能**开启投机路径。`pld_enabled = use_spec && ...`，而
`use_spec` 需要 `MYDS_BATCH2_SPEC` 或 `DSPARK_DEPTH=2`。
所以真正要 A/B 的是 `MYDS_BATCH2_SPEC`，不是 `MYDS_PLD`。这一点在
§4.7 里决定了整个实验设计。

### 4.7 生产 A/B 实测（macstudio 8187，2026-11-01）

> 这一节把 §4.5 里「验不了」的那项补上了。方法、数据、以及**被推翻的判断**都在这里。

**口径（任一不同则不可比）**：同一进程同一端口串行重启，同一批 3 个 prompt
（中文散文/英文技术/代码），`max_tokens=512`、`temperature=0`、无并发、
`MYDS_DSPARK=0`、`MYDS_PREFIX_CACHE=1`。每臂 3 轮 × 3 任务 = 9 样本。
速度取自服务端自己日志的 `decode: N tok in X s = Y t/s`，不靠客户端计时。

| 臂 | 配置 | prose_cn | prose_en | code | **中位 t/s** | 相对 A |
|---|---|---:|---:|---:|---:|---:|
| **A** | `MYDS_BATCH2_SPEC=0`（生产） | 42.00 | 42.00 | 42.00 | **42.00** | — |
| **B** | `MYDS_BATCH2_SPEC=1` | 39.00 | 39.80 | 37.70 | **39.00** | **−7.1%** |
| **C** | B + `MYDS_SPEC_ADAPTIVE=1` | 42.00 | 42.00 | 42.00 | **42.00** | **0.0%** |
| **A2** | 复原 A（验证无残留） | 42.10 | 42.00 | 42.10 | **42.10** | +0.2%（噪声） |

A 与 A2 一致 ⇒ 配置复原干净，无残留。A 臂 9/9 全部 42.00，测量噪声 < 0.5%。

**机理证据（同一批请求的服务端计数）**：

| 臂 | PLD cycles | 接受 | 接受率 | 验证成本 |
|---|---:|---:|---:|---:|
| B | 58 / 42 / 107 | 21 / 15 / 53 | **36.2% / 35.7% / 49.5%** | 48.4–48.7 ms/call（gpu 44.2–44.5） |
| C | 20 / 5 / 31 | 9 / 5 / 17 | **45.0% / 100% / 54.8%** | 48.0–49.7 ms/call |

- 基线单步：1000 / 42.00 = **23.81 ms/token**
- 验证成本：**48.5 ms/call** ⇒ **2.04×**
- 账本 §100.3 记的 2.09× **复现了**（误差 2.4%）

**三条结论**：

1. **−6.6% 这个数字是真的。** B 臂 39.00 对 A 臂 42.00 = −7.1%，同一量级、
   同一方向、接受率 36% 与账本的 37.3% 吻合。原提交的靶子没打错。
2. **门禁确实有效，是止损而非加速。** C 臂把 −7.1% 压回 0.0%，
   且接受率从 36% 升到 45–100% —— 它砍掉的正是低质量桶。
   注意 C 臂第一轮是 41.1/41.1/40.8，第二三轮才回到 42.0：
   **这就是 `SPEC_ADAPTIVE_MIN_SAMPLES=3` 在起作用**（先强制试探再门禁），
   没有这个下限，桶 0 一次都不会发草稿，EMA 永远停在先验上。
3. **但结构上不可能为正。** 48.5/2 = 24.25 ms/token > 23.81 ms，
   即**接受率 100% 时仍然慢 1.9%**。所以「自适应投机控制器」这个词夸大了：
   它只能把投机从「净亏 7%」救成「不亏」，永远救不成「赚」。

**⇒ 裁定不变，但理由要改准**：默认关闭的理由不是「门禁没用」，
而是「最好的情况也只是打平，而打平意味着关掉更简单」。
若将来验证器成本降到 < 2× 单步，这个门禁才有加速意义 —— 那时它会自动开始放行。
代码就此保留，作为那条路径的现成开关。

**顺带否掉一件事**：`MYDS_PLD=1` 在生产配置里存在了几个月却等于没开
（A 臂行为与 A2 完全相同、`PLD speculative` 日志 0 行）。这与账本 §77.x 的
记录一致，不是新问题，但值得在配置里加注释，免得下次又有人以为它在跑。
