# 0-ULP 与非 0-ULP：状态、开关、日志与门禁

本文是「哪些开关会改变输出、它们各自的实际风险、以及用什么证据判断」的单一入口。
**结论全部来自实测，不是从代码推断的。**

最后更新：2026-10-25

---

## 0. 一句话结论

**0-ULP 不是安全保障，是一条未经验证的禁令。**
它曾经把整类「少算」方案挡在门外，而其中一部分（YOCO COMPACT）实测质量正常；
另一部分（indexer 窗口）实测会静默编造。
**⇒ 每个近似开关必须单独测质量，不能靠「是否 0-ULP」一概判断。**

| 开关 | 默认 | 是否改输出 | 状态 | 证据 |
|---|---|---|---|---|
| `MYDS_YOCO_COMPACT` | `0` | 是 | **可用**（短上下文） | 账本 §98 |
| `MYDS_INDEXER_KEY_WINDOW` | 未设 | 是 | **禁止** | 账本 §98 |
| `MYDS_MOE_EXPERTZ_DS` | `0` | 是 | 未采纳（+0.82%，非 0-ULP） | 账本 §20 |

**「是否改输出」这一列的区别很重要**：
`MYDS_PROMPT_MASK_BITS` 也是「非 0-ULP 风格」的开关（改实现不改结果），
但它**语义等价**，属于 0-ULP。不要把它和近似开关混为一谈。

## 2. YOCO COMPACT（`MYDS_YOCO_COMPACT=1`）

### 2.1 它做什么

consumer 层（21..39）只计算末尾保留区，跳过保留区之前的块。
Layer 20 仍生产**全序列**压缩 KV，所以远距离信息经压缩 KV 依然可达。

```
sh_loop_rel = (il == 20u) ? 0u : sh_full_rel;
               ↑ 层20 从 0 跑全序列      ↑ 其余层直接跳到保留区
```

### 2.2 实测收益（同 prompt、`--temp 0`、单请求）

| prompt | YOCO=0 | YOCO=1 | 收益 |
|---|---:|---:|---:|
| 5,866 tok | 13.01 s | 10.39 s | **−20.1%** |
| 25,066 tok | 44.45 s | 39.02 s | −12.2% |
| 55,666 tok | 96.50 s | 89.90 s | −6.8% |

**上下文越长收益越小**，且被 indexer 窗口在长上下文时完全淹没
（55K 时叠加 window=4096 只有 82.00 s，比单独 window=2048 的 81.94 s 还慢）。

### 2.3 实测质量

**大海捞针探针**（18,920 tok，第 1 条记录埋「ZEPHYR-7734 / 林工」，末尾提问）：

```
基线（无窗口）    → 林工   ✅
YOCO COMPACT     → 林工   ✅   ← 与基线一致
```

**代码审计四格对照**（testcase34，每格 1 次）：

| 臂 | thinking | ULP | 得分 |
|---|---|---|---:|
| 8187 | off | 0-ULP | 8.1 |
| 8188 | off | **非0-ULP** | **7.7**（最低） |
| 8189 | on | 0-ULP | 8.4 |
| **8190** | **on** | **非0-ULP** | **8.6**（最高） |

**结论：YOCO 配 thinking on 最好，配 thinking off 最差。**
7 类核心安全发现四臂 7/7 一致（命令注入 / SQL 注入 / 路径遍历 /
pickle 反序列化 / 硬编码密钥 / 无盐 MD5 / 文件句柄泄漏）。

### 2.4 日志

开启后每个请求首次触发时打印一次：

```
[WARN] V4.1 suffix shrink[YOCO COMPACT — 近似，非 0-ULP]: keep_tokens=512,
       其中前 127 个仅用于窗口预热（输出不精确），可信区间 = 末尾 385 个
       (total=18922, consumer start=17898)
```

**这条日志是判断「YOCO 是否真的生效」的唯一依据**——光看配置不够，
因为 `MYDS_*` 会被配置文件无条件覆盖（见 §5）。

### 2.5 单元测试

`tests/test_yoco_compact.c`（121 行）

> ⚠️ **范围声明**：这是**公式复算**，不调用引擎、不跑前向、不比对输出。
> 它把 `sh_need` / `s_global` 的算式重新实现一遍再断言自洽。
> **能抓**：算式被改错（keep 忘了减、边界夹取写反）。
> **不能证明**：开关两臂的行为等价性。

**真正的行为验证** = §2.3 的 needle + 代码审计，不是这个单测。

## 3. Indexer key 窗口（`MYDS_INDEXER_KEY_WINDOW=N`）—— 禁止生产使用

### 3.1 它做什么

只让距可见上限最近的 N 个压缩键参与打分，更早的填 `-INF`。
复杂度从 O(N²) 降到 O(N×window)。

### 3.2 收益（55,666 tok）

| 配置 | prefill | 相对基线 |
|---|---:|---:|
| 基线 | 96.50 s | — |
| window=8192 | 85.29 s | −11.6% |
| window=4096 | 83.18 s | −13.8% |
| window=2048 | 81.94 s | **−15.1%** |

**比 YOCO 快**（15.1% vs 6.8%），但——

### 3.3 质量：会让模型静默编造

同一个大海捞针探针：

| 配置 | 回答 | 判定 |
|---|---|---|
| 基线 | `林工` | ✅ |
| window=512 | `无法确定，因为提供的项目代号中没有包含负责人信息。` | ❌ 诚实失败 |
| **window=4096** | **`张伟`** | ❌❌ **编造** |
| window=8192 | `ZEPHYR-7734 的负责人是……（此处应填写姓名，但无法` | ❌ 诚实失败 |

**⇒ 不要调大窗口就以为安全。只要 needle 落在窗口外就必然失败；
窗口大小只决定「编」还是「认」，与安全性无关。**

### 3.4 日志

```
[WARN] indexer: key 方向窗口 4096（非 0-ULP —— 更早的压缩键不参与 top-k）
```

### 3.5 单元测试

`tests/test_indexer_window.c`（346 行），`make test` 在 window 0/8/20 三档各跑一次。

断言三件事：

1. `first_row` 与控制台公式自洽
2. 窗口**内**的行与参考臂（direct 内核，不读 window）数值一致
3. 窗口**外**的行必须恰好是 `-INFINITY`
4. **防空转**：window>0 且 token 数超窗时，必须真的排除过行

覆盖两条路径：chunk（prefill）与 one_direct（decode），外加跨路径一致性。

**这个测试能证明窗口语义正确，但证明不了它对模型质量的影响**——
后者只能靠 §3.3 的 needle 类探针。

## 4. `MYDS_PREFIX_CACHE` —— 稳定性的关键，不是精度开关

严格说它不改输出（续跑与全量重放逐位一致），但**误关它的代价极大**。

### 4.1 实测代价

一份 141 行代码的审计（32 轮工具调用，上下文 3.2K → 29.5K）：

| | 关闭 | 开启 |
|---|---:|---:|
| prefill 累计 | **509,559 tok** | 6,776 tok |
| prefill 耗时 | **878 s** | 22 s |
| 单份总耗时 | 20.0 min | **4.1 min** |

**命中率 80%–97%。** 关掉它，每一轮都从 0 重新 prefill 整个上下文。

### 4.2 与「采样独立」的关系（重要）

**采样独立性由「每轮冷启动」保证，不需要关 prefix cache。**

```
restart_per_run → 新进程 ⇒ pcache_len = 0 ⇒ 首个请求必然全量 prefill
```

跨轮真正会残留的是**磁盘**上的 `kvlow`，那由 `kv_storage_clean` 每轮删除。
两者职责不同，不要混用。

### 4.3 日志

```
[INFO] prefix cache: off (MYDS_PREFIX_CACHE=0)
[INFO] prefix cache: nothing cached yet (this is the first request)
[INFO] prefix cache: prompt 71297 tok, cached 71163, common prefix 71163 -> resume from cached prefix
[INFO] prefix cache: skipped - common prefix 11 of cached 43, but no snapshot within it
```

**每一次都必须说话**——优化不生效时沉默是最贵的输出。

## 5. `myds.conf` 是唯一真源（会覆盖环境变量）

`src/myds_configfile.c:85`：

```c
/* 配置文件是 MYDS_* 的唯一来源：读到什么就写什么，无条件 setenv。
 * 进程启动时的环境变量里即使有同名项，也会被这里直接覆盖，且不产生任何日志 */
if (setenv(key, val, 1) != 0) { ... }
```

**⇒ 想用环境变量临时开某个开关，必须先确认它没写在 `myds.conf` 里。**

### 5.1 例外：`--config` 可以叠加

`src/main.c` 的 `load_config_early` 支持重复 `--config`，按顺序加载、后者覆盖前者：

```bash
--config myds.conf --config myds.conf.non0ulp
```

**叠加层只写差异行**，主文件仍是唯一全量真源——两份全量配置必然漂移，
而漂移意味着「对比实验的变量不止一个」。

`fleet.conf` 第 19 列 `MYDS_CONF_EXTRA` 就是给这个用的。

### 5.2 仍会绕过配置的例外

`fleet.conf` 的 TEMP/TOP_P/TOP_K/MIN_P/REP_PEN/THINKING/EFFORT 列
会以**命令行参数**（优先级高于配置文件）传给引擎：

```zsh
[[ -n "$TOP_K" ]] && CMD_ARGS+=(--top-k "$TOP_K")
```

**⇒ `myds.conf` 里的 `MYDS_TOP_K` / `MYDS_MIN_P` 对 fleet 启动的服务是死配置。**
改采样参数要改 `fleet.conf`，不是 `myds.conf`。

## 6. MoE 专家权重观测（`MYDS_MOE_WEIGHT_HIST=1`）

**纯观测，不改任何计算。** 但它做 readback，会同步 GPU。

### 6.1 它回答什么

「top-k 里最弱的专家权重到底多小」——这决定能否自适应截断以减少 MoE 字节。

### 6.2 结论（已关闭该方向）

| 阈值 | 平均可跳槽位 | 字节占比 |
|---|---:|---:|
| < 1e-2 | 0.18 | **3.1%** |
| < 2e-1 | 2.98 | 49.6%（但丢的是真参与的专家） |

**中间无甜点区**，安全档只给 +1.2% decode。详见账本 §99。

### 6.3 三个必须知道的坑（都踩过）

1. **`barrier_buffer` 不等于等 GPU 完成**：必须 `flush → commit → begin` 三步，
   否则读到的是**全零**
2. **每行权重和的期望值 = `routed_scaling_factor`（当前 1.50），不是 1.0**
3. **布局不确定时先打原始 float 样本**，比设计十个直方图都快

## 7. 队列与计时的口径（不是 ULP 问题，但同样会误导判断）

### 7.1 排队时间必须与推理时间分开

`wall` 曾经把等锁时间算进去，导致并发时看起来像引擎退化。

现在三者分开：

```
wall: 3.0s (infer 3.0s, queue 0.0s)
```

- `wall` = 端到端（客户端看到的，**含**排队，外部监控拿它对比）
- `infer` = 拿到推理名额之后（引擎实际消耗）
- `queue` = 等名额的时间

decode 吞吐按 `infer` 算，不是 `wall`。

### 7.2 客户端断连不是服务端错误

`finish_reason: cancelled` ≠ `error`。流式与非流式两条路径都已区分。

### 7.3 prefill 统计必须属于本请求

`myds_last_prefill_stats` 有 `valid` 字段；不是本请求写的就返回全零。
否则会打出「prompt: 0 tok, prefill: FAILED after 15815 tok」这种自相矛盾的行
（那 15815 是上一个请求的）。

## 8. 做质量验证的标准做法

任何非 0-ULP 改动，**在谈性能之前**先过这两关：

### 8.1 大海捞针（必须）

构造 18K–50K token 的 prompt，第 1 条记录埋一个唯一事实，中间大量无关内容，末尾提问。

**判据**：能准确回答 ⇒ 长距离检索完好。答错或编造 ⇒ 禁止。

**为什么必须用这个而不是困惑度**：困惑度对「检索失败」不敏感，
而检索失败正是这类近似的最大风险。

### 8.2 代码审计对照（可选，用于确认无系统性退化）

`autoreview` 跑同一项目，双格对照，看核心发现是否一致。

**注意口径**：两次生成的报告长度可能差 87%，导致后续 prompt 序列完全不同。
**耗时数据不能跨格比较**，只能比内容。

## 9. 已证否的方向（避免重复投入）

| 方案 | 理论 | 实测 | 结论 |
|---|---:|---:|---|
| D1 flash-decoding | +4~8% | **−4.4%** | 证否 |
| D2 rmsnorm→GEMV 融合 | −61% µbench | **0%** 端到端 | 证否 |
| D3 专家进 grid.z | +26%（外推） | **+0.82%**，且非 0-ULP | 证否 |
| 专家权重截断 | 最多 +5% | **+1.2%** | 证否 |
| PLD / batch2 投机 | — | **−6.6%**（接受率 37.3%） | 倒亏 |
| indexer 窗口 | +15.1% | 质量失败 | **禁止** |

**decode 的 43 t/s 已接近这套架构 + 这个量化形态的上限**
（dense 70.6% 峰值，GPU 驻留 100%、满频 1398 MHz）。
