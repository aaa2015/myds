# 同机反代下的回环/令牌验证（账本 §129）

## 先纠正前提：这台机器没有反代

`ssh macstudio` 实测：

| 项 | 结果 |
|---|---|
| 8187 监听 | `myds` 直接绑 `*:8187`（**所有接口**） |
| 反向代理进程 | **无**（nginx/caddy/haproxy/traefik/envoy 都查过） |
| 防火墙 | **已关闭** |
| 隧道/端口转发 | 无 |
| 地址 | `192.168.88.192`（私网） |

⇒ **§123 里"同机反代可绕过回环门"在理论上成立，但对当前部署不适用**——
没有反代，那个绕过路径不存在。

## 但暴露面是另一回事

从 macmini（LAN 内另一台机器）实测：

```
GET  /v1/models          -> 200
GET  /debug/state        -> 404   （默认关闭，正确）
POST /v1/chat/completions -> 200  {"content":"OK"}
```

**推理端点本身无鉴权、监听所有接口、防火墙关闭。** 同一网段任何人都能用这台机器的模型。
这解释了"跑了几个月没反馈"——它一直是这个状态，且网段是私网。

## 令牌门在同机反代下仍然有效（5/5）

用 Python 写一个转发代理监听 18187、转发到 `127.0.0.1:8187`——
**服务端观察到的 peer 就是 127.0.0.1**，正是 §123 描述的条件。

| 检查 | 结果 |
|---|---|
| 直连 + 令牌 | 200 |
| 直连无令牌 | 404 |
| **经代理但代理不转发令牌** | **404**（安全保持） |
| **经代理且转发令牌** | **200**（可用性保持） |
| 经代理 + 错误令牌 | 404 |

**关键：代理剥掉令牌时被拒。** 说明门不是"信任来源地址"，而是"要求凭证"。

## 测试自身的 bug（被测试抓到）

第一轮 `proxy_wrong_token_refused` 返回 200 判 FAIL。查下去是**我的测试写错了**：
"错误令牌"字面量恰好等于正确令牌（都是 3 字符），显示时被脱敏所以看不出来。
已改成 `WRONG_TOKEN = TOKEN + "-but-longer"`，程序化保证不同，重跑 5/5 通过。

**这不是门的漏洞，是负向用例没有构造出差异。** 与 §121 同类：
一个测不出目标现象的用例，会给出干净的假结论——区别是这次它自己报了 FAIL。

## 结论

1. `/debug/state` **现在没有问题**：默认关闭，即使开启也需 loopback + 令牌。
2. 令牌门在反代场景下**有效**，且不依赖 peer 地址。
3. **真正的暴露面是推理端点本身**：无鉴权、全接口监听、防火墙关闭。
   要不要收紧是另一个决定——但在那之前，`/debug/state` 的防护属于"给已经敞开的门再加一把锁"。

## 建议（按成本排序）

1. **把 8187 绑定改回 `127.0.0.1`**，需要 LAN 访问时用反代（带上令牌）。
   这是唯一能真正限制"谁能用模型"的动作。
2. 打开防火墙，只放行必要端口。
3. `/debug/state` 保持默认关闭（现状）。

原始：`proxy-gate.jsonl`。
